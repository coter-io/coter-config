# Proposal

## Why

`docker/docker-compose.yml` carries `env_file: .env` on the `openclaw-gateway` service, which injects **every** key of the operator's `.env` into the container — including `OPENCLAW_CONFIG_DIR` and `OPENCLAW_WORKSPACE_DIR`, which exist only to name the *host* side of the bind mounts and hold VPS paths. The gateway honours them as its own writable directories, so inside the container it resolves state writes to `/home/openclaw/...`, where `/home` is root-owned and the process is uid 1000. Every inbound Telegram message on the production VPS dead-letters with `EACCES: permission denied, mkdir '/home/openclaw'` and retries forever; the gateway starts, polls and receives, but can never reply.

The same defect was found and fixed in `docker/docker-compose.local.yml` for local runs only. The shipped compose file a deployment consumes was left unfixed, so the bug is live in production while the repository already documents its cause.

## What Changes

- Remove `env_file: .env` from the `openclaw-gateway` service in `docker/docker-compose.yml`. Its `environment:` block already enumerates every variable `config/openclaw.json` and the installed skills consume, and `${VAR}` interpolation reads `.env` through a separate mechanism, so bind-mount sources and the image reference keep working. This ends blanket injection as a class rather than patching the two names currently known to collide.
- Pin `OPENCLAW_CONFIG_DIR` and `OPENCLAW_WORKSPACE_DIR` in that `environment:` block to the in-container mount targets (`/home/node/.openclaw` and `/home/node/.openclaw/workspace`), as a positive assertion rather than relying on the absence of an injection path.
- Document in `docker/.env.example` that the two directory variables name host paths consumed by compose, not values passed to the container.
- Extend `scripts/check-env-vars.sh` with a fourth check: every `${VAR}` referenced by `config/openclaw.json` must appear as a key in the deployment compose file's `environment:` block. Without blanket injection, a variable the config references but compose does not pass would reach the gateway empty, and nothing currently detects that.
- Correct `scripts/check-env-file.sh`, whose "set but not declared" warning asserts that an undeclared name "reaches no container". With `env_file` present that claim was false — it is how `OPENCLAW_GATEWAY_BIND=0.0.0.0` and `OPENCLAW_GATEWAY_PORT` reached the production gateway while being declared in neither the compose file nor `docker/.env.example`.
- Reconcile `docker/docker-compose.local.yml`: its directory pins become redundant and its comment block, which explains the inherited `env_file` as load-bearing, becomes wrong. The local stack must keep working with no behavioural change.

### Out of scope

- **Renaming the directory variables** to `OPENCLAW_HOST_*` so one name cannot mean two things. This is the cleaner naming, but `.env` on the VPS is generated by a separate infra repository, so the rename needs cross-repo coordination. The pin plus the removal of `env_file` makes the collision harmless in the meantime.
- **A deployment write smoke check** asserting the gateway can write its state directory at bring-up. This is what would have caught the defect at deploy time instead of as a silent outage, and it would also catch the next failure in line (the host directory not being owned by uid 1000). It is a new capability rather than a correction to this one.
- **Retry and dead-letter behaviour.** One update retried indefinitely with no ceiling and no operator-visible signal. That is upstream gateway behaviour, not this repository's configuration.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `deployment-env-contract`: The contract currently governs only which variable *names* are documented and whether they match across files. It is silent on which variables may cross into the container, which is the gap this defect fell through: both colliding names were correctly documented and correctly spelled. Gains requirements that the container receives a declared set rather than the whole environment file, that the gateway's writable directories resolve to paths inside the container, that every variable the config references is passed explicitly, and that these are enforced by the existing scripts.

## Impact

- `docker/docker-compose.yml` — `env_file` removed from the gateway service; two directory variables pinned. The `workspace-sync` service carries no `env_file` and is unaffected.
- `docker/docker-compose.local.yml` — redundant pins and a now-incorrect comment block.
- `docker/.env.example` — host-only variables marked as such.
- `scripts/check-env-vars.sh`, `scripts/check-env-file.sh` — one new check, one corrected claim. Both already run in the pull request gate, the pre-commit hook and the release build, and `config-pr-validation` requires the gate to pick up a strengthened script with no workflow edit, so no workflow change is needed.
- `CONTRIBUTING.md` — the environment-variable contract section describes what the checks enforce.
- **Behavioural consequence to verify on deployment:** `OPENCLAW_GATEWAY_BIND=0.0.0.0` and `OPENCLAW_GATEWAY_PORT` will stop reaching the container. The shipped `command:` already passes `--bind lan --port 18789` explicitly and the published port is loopback-only, so the gateway must remain reachable at `127.0.0.1:18789`.
- **Operator steps outside the repository:** spooled updates replay as a burst of belated replies on the first successful start, and the host directory behind the mount must be owned by uid 1000. Neither is a code change; both belong in the deployment runbook.
