# Design

## Context

See `proposal.md` — Why. The constraints that shape the approach, each verified against the current tree or against the running deployment:

- **Two mechanisms read `.env`, and only one of them is the defect.** Compose's `${VAR}` interpolation reads the project environment file to render the compose file itself; the service key `env_file:` is a separate instruction to copy that file's keys into the container's process environment. Removing `env_file:` therefore leaves bind-mount sources and the `image:` reference intact. The archived `add-local-dev-stack` design records the same separation from the opposite direction.
- **The gateway's `environment:` block is already complete.** Every `${VAR}` in `config/openclaw.json` — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_USER_ID`, `OPENROUTER_API_KEY`, `COMPOSIO_MCP_URL`, `COMPOSIO_API_KEY` — is named there, as are the credentials only the skills use (`GH_TOKEN`, `BRAVE_API_KEY`, `ANTHROPIC_API_KEY`) and the gateway's own token. Nothing the gateway needs arrives solely by blanket injection. This is what makes removal viable rather than merely desirable.
- **`workspace-sync` is already correct.** It carries no `env_file:` and enumerates its four variables explicitly, so `GIT_WORKSPACE_TOKEN` never entered the gateway through that service. It entered through the gateway's own `env_file:`.
- **Four variables are crossing today, not two.** Measured on the production VPS: `OPENCLAW_CONFIG_DIR` and `OPENCLAW_WORKSPACE_DIR` hold host paths, and `OPENCLAW_GATEWAY_BIND=0.0.0.0` plus `OPENCLAW_GATEWAY_PORT=18789` are declared in neither `docker/docker-compose.yml` nor `docker/.env.example`. `HOME` is correctly pinned to `/home/node`. The operator's `.env` is generated by a separate infra repository and holds keys the documented contract does not describe.
- **`check-env-file.sh` already had the signal and discarded it.** Its "set but not declared" branch is a warning, justified in-comment by the claim that such a name "reaches no container". With `env_file:` present that claim was false, which is why the only check positioned to catch `OPENCLAW_GATEWAY_BIND` reported it as harmless. The check also runs only from `local.sh`, never on the VPS.
- **One name carries two meanings, and that cannot be fixed here.** `OPENCLAW_CONFIG_DIR` is simultaneously the host bind-mount source and a value the gateway honours. An operator cannot resolve the conflict by editing `.env`: setting it to the in-container path would make the VPS bind-mount `/home/node/.openclaw` from the host. The rename that would separate the meanings needs the infra repository, so the fix must live entirely in this repository's compose file.
- **The local stack inherits whatever the shipped file does.** `docker/docker-compose.local.yml` deliberately overrides nothing about `env_file:` and documents the inherited key as sufficient. Removing it from the shipped file changes the local stack too.
- **The container runs as uid 1000 (`node`).** `docker/Dockerfile` sets `USER node` and chowns `/home/node/.openclaw`. `/home` itself is root-owned and mode 0755, which is why `mkdir '/home/openclaw'` fails rather than succeeding somewhere harmless.

## Goals / Non-Goals

**Goals:**

- Make it structurally impossible for a value intended for the host to be read by the gateway as its own, rather than correcting the two names currently known to collide.
- Keep the fix inside `docker/docker-compose.yml` so a deployment picks it up by copying one file, with no coordinated change to the infra repository that generates `.env`.
- Leave the local stack's observable behaviour unchanged, and leave the shipped file as the thing the local stack exercises.
- Make the invariant the removal depends on — that the compose file names everything the config references — enforced rather than remembered.

**Non-Goals:**

- Auditing what else the operator's `.env` contains. The approach makes the contents irrelevant to the container, which is a stronger result than enumerating them.
- Changing how configuration is delivered to the mounted directory. `make push-config` in the infra repository is untouched.
- Hardening the gateway's bind address. `OPENCLAW_GATEWAY_BIND` stops reaching the container as a consequence of this change, not as its purpose.

## Decisions

**Remove `env_file:` rather than pin the colliding names.**
Pinning the two directory variables in `environment:` works — an `environment:` entry beats `env_file:`, which is how the local override already fixes it — but it fixes two names out of an open set. The production environment already carries two more undeclared names that cross into the container, and `.env` is generated elsewhere, so the set grows without this repository's involvement. Removal inverts the default from "everything crosses unless overridden" to "nothing crosses unless named". Considered and rejected: keeping `env_file:` and adding a check that every key in `.env.example` is either pinned or known-safe. That check would have to reason about a file the deployment does not even use, since the VPS `.env` is generated and already diverges from it.

**Pin the two directory variables anyway.**
Redundant once `env_file:` is gone, and kept deliberately. It states the intended in-container paths where a reader of the compose file will look for them, rather than leaving correctness resting on the absence of a line. It also keeps the shipped file and the local override expressing the same thing, so the two stacks cannot drift back apart. The cost is two lines and a comment.

**Enforce the invariant in `check-env-vars.sh`, not in a new script.**
Removal is safe only while `environment:` names everything `config/openclaw.json` references. That is exactly the kind of three-way name comparison `check-env-vars.sh` already performs, and `config-pr-validation` requires the pull request gate to pick up a strengthened script with no workflow edit. A new script would need wiring into the hook, the gate and the release build, and could disagree with the existing one about what "referenced" means. Note the new check reads the `environment:` block specifically, not the whole compose file: a variable that appears only as a bind-mount source must *not* satisfy it.

**Correct `check-env-file.sh`'s reasoning but leave its severity alone.**
Once `env_file:` is gone, "nothing reads this name" becomes true again, and the warning is correctly a warning: `.env` legitimately carries values compose consumes on the host. The fix is to the comment's justification and the message's wording, so the next reader does not re-derive a false premise. Considered and rejected: promoting it to an error. It would fail on `GHCR_USERNAME`, which `.env.example` declares and no container reads.

**Treat the bind-address change as a verification step, not a design choice.**
With `env_file:` removed, the gateway runs with the `--bind lan --port 18789` its shipped `command:` already passes, instead of under an undeclared `OPENCLAW_GATEWAY_BIND=0.0.0.0`. The published port is `127.0.0.1:18789` either way, so external reachability is unchanged by construction; what must be confirmed is that the gateway still binds an interface the published port can reach from the host. This is checked after deployment rather than reasoned about, because the precedence between the flag and the variable is an upstream behaviour this repository does not control.

## Risks / Trade-offs

- **A variable only the running gateway needed, which nobody enumerated, silently disappears.** → The new `check-env-vars.sh` check covers everything `config/openclaw.json` references. It cannot cover a variable an installed skill reads directly, because that is not visible in any file here. Mitigated by reading the gateway's environment before and after on the VPS and diffing it, so every variable that stops arriving is seen rather than inferred — the same `docker compose exec ... env` measurement that confirmed the diagnosis.
- **The gateway becomes unreachable because the effective bind address changes.** → Verified immediately after deployment against `127.0.0.1:18789` from the VPS host. Rollback is restoring the previous compose file, which is a single file copy and a restart.
- **Spooled updates replay as a burst of belated replies on the first successful start.** → Expected, not prevented: those messages were accepted and never answered, so answering them is correct. Called out in the runbook so the operator is not surprised, with the option to clear the spool first.
- **The next permission failure is already queued.** → With writes landing in `/home/node/.openclaw`, they reach the bind mount of `/home/openclaw/.openclaw`, which must be owned by uid 1000. If it is not, the same `EACCES` returns with a `/home/node/...` path. Checked as a precondition rather than discovered afterwards.
- **The redundant pins invite a future reader to delete one half of the fix.** → Both the removal and the pins carry comments naming the other, so neither reads as unexplained.
- **One name still means two things.** → Accepted for now. The compose file makes the collision inert, but an operator reading `.env` can still misread `OPENCLAW_CONFIG_DIR` as a container path. The `.env.example` wording is the mitigation; the rename is deferred to a cross-repo change.

## Migration Plan

1. Land the repository change; the pull request gate runs the strengthened checks.
2. Capture the gateway's current environment on the VPS (`docker compose exec openclaw-gateway env`) as the before-state for the diff.
3. Confirm the host directory behind the mount is owned by uid 1000.
4. Copy the new `docker/docker-compose.yml` to the VPS and recreate the gateway service.
5. Capture the environment again and diff: the four host-side and undeclared names must be gone, the four directory and home values must name in-container paths, and no credential the config references may have disappeared.
6. Confirm the gateway answers on `127.0.0.1:18789`, then send a message and confirm a reply.
7. Rollback: restore the previous compose file and recreate the service. No state migration is involved, so rollback is complete rather than partial.

## Open Questions

- Whether the spool should be cleared before the first successful start or allowed to replay. This is the operator's call at deployment time and changes neither the specs, the approach, nor the tasks.
